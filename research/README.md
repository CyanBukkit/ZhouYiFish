# 周易规则会不会提高事件预测：一个可复现的探索模块

**四臂模型实验没有运行。OASIS 群体仿真没有接通。** 本目录不是一次已经完成的 MiroFish 增强实验。臂 A 若将来运行，只是聊天补全基线，不是原版 MiroFish。目前没有证据可以说规则让预测更准。

这是一项探索性研究。它问的是：把一套事先写死的传统起卦计数交给预测流程以后，事件级概率会不会比对照更好。它不假设答案是“会”。

这里没有预测保证。结果不能用于医疗、博彩或投资决策。本仓库不宣称玄学、周易或梅花易数已经被科学验证。工程链路能够跑通，也不等于预测是对的。

离线数字以 `research/experiments/offline_v1/实验说明.md` 为准，并且只按探索性区间阅读。不要把极端次数 0 写成 p<0.0001，也不要把 Holm 读成对 0.02 的检验。

## 和 MiroFish 的关系

本仓库的网页应用来自 [MiroFish](https://github.com/666ghj/MiroFish)（AGPL-3.0）。研究代码放在 `research/`，不改那套前后端，也不改上游仓库。MiroFish 的仿真由 OASIS 驱动。**本模块没有运行 OASIS，也没有接通 Zep 或报告代理。**

许可和署名见 `research/NOTICE.md`。农历库 zhdate 是 GPL-3.0-or-later。

## 冻结的问题

只做一个能结算的二元题：

> 在 Asia/Shanghai 的某一个公历日，请求坐标（31.2304N, 121.4737E）所对应的结算网格上，当日降水量合计是否达到或超过 1.0 毫米？

事先写死、评分前不再改的内容：

| 项目 | 规定 |
| --- | --- |
| 入组 | 窗口内的每一个公历日一行，不按结局或卦象剔除 |
| 信息时间 | 当天 00:00，Asia/Shanghai |
| 可用信息 | 这个时点、固定坐标、题面和本协议 |
| 禁用信息 | 降水量、天气预报、结局，以及时点之后才有的资料 |
| 唯一结算 | Open-Meteo 历史接口的 `precipitation_sum`，时区 Asia/Shanghai |
| 缺测和争议 | 没有第二来源，不人工改数；空值保留、不填补、不打分 |
| 先导期 | 2022-01-01 至 2022-12-31，只拟合基率 |
| 留出集 | 2023-01-01 至 2023-12-31，只分析一次 |
| 停止 | 不因结果去加年份、改阈值或改概率映射 |
| 最小实际增益 | 配对 Brier 差 0.02 |
| 等效性 | 没有做。区间含 0 不是等效 |

完整文本、引文和哈希在 `research/protocol/protocol_v1.json`。程序启动时核对 `protocol_v1.sha256`。

主终点是独立事件上，聊天基线臂 A 与规则文本臂 B 的配对 Brier 差，越低越好，并报告常数基率。臂 A 不是原版 MiroFish。本次没有模型凭据，这个主终点**没有运行**。离线部分只跑了规则、公开数据和评分器。评估标签是：预设代码分割的回顾性评估，研究者选择泄漏未排除。没有外部时间证据证明研究者从未看过 2023 年的降水，或没有试过别的映射。

## 规则：只做卷一年月日时

来源是维基文库公开转录，不是校勘定本：

<https://zh.wikisource.org/zh-hans/梅花易數/卷一>

转录里有「康节先生」的叙事。这不能写成邵雍确证亲著。作者归属仍有争议，本仓库不下这个结论。

核对过的观梅占算例：

> 辰年五数，十二月十二数，十七日十七数，共三十四数……馀二，属兑，为上卦，加申时九数，总得四十三数……馀得三数，为离，作下卦。……馀一为动爻，是为泽火革。初爻变咸。

对应计算：年支 5，月 12，日 17，时支 9。上卦兑，下卦离，动爻 1。六爻自下而上为 `1,0,1,1,1,0`，初爻翻转后是泽山咸。这是单元测试，不是把故事里的断语当成标签。

卦数用先天数：乾 1、兑 2、离 3、震 4、巽 5、坎 6、艮 7、坤 8。这个编号不等于六爻二进制的整数值。后天数、揲蓍、体用五行和象辞都不进入概率。

八除若整除，转录写的是「如得八数整，即坤卦」。六除的转录要求用余数作动爻，但没有单独写明余数为零时就是上爻。余数零记作第 6 爻，是本协议的边界约定，**不是原文引句**。

P-MAP-1 是工程假设：`(本卦阳爻数 + 1) / 8`。它只用本卦六爻，不用卦名、变卦、动爻、断语或结局。它不是古法给出的概率，也不是有传统依据的预测模型。

## 历法政策

这些是工程约定，不是“唯一古法”：

- 法定时区 `Asia/Shanghai`，同时记下 UTC 时间和实际偏移。1988 年夏令时会记成 +09:00，不把偏移写死成永远 +08:00
- 公历日界是当地 0 点。23 点仍用当天的农历日数，时支已经是子
- 农历年和年支在春节切换，不在立春，也不在公历 1 月 1 日
- 闰月使用同名月的月数。闰二月和二月都把 2 加进总数，闰月标记只作审计，不另加一数
- 因此同一个年支、同月数、同日、同时支会得到同一卦。闰二月初一的 0 点和二月初一的 0 点就是这样
- 农历来自 zhdate 0.1。边界日期用香港天文台对照表核过，见 `DATA_SOURCES.md`。库换版本会直接拒绝运行
- 时间起卦是确定函数，没有 seed。不能事后改时间再挑一卦

奇门和风水没有严格算法，调用会明确失败，不会返回一个看起来像结果的占位卦。

## 为什么要有日历基线

年月日时起卦在固定时点上就是日历的函数。若它赢过“全年一个常数”，差出来的可能只是季节。所以离线对照在常数基率之外，还有：

1. 只用先导期、按农历月估计的发生率。闰月并进同名月
2. 在每个农历月内部，用固定的 HMAC-SHA256 Fisher-Yates 打乱规则概率。编码是 UTF-8，计数器是 8 字节大端。打乱保留该月概率的多重集，不是换成 0.5 这种稻草人

真实的时间和坐标在各臂是同一份。随机对照改的是规则输出的搭配，不是另外编一套时间或地点。

同一时点重复起卦得到同一卦。多个智能体共用这一卦时，不能把智能体数当成独立样本。协议规定先聚合成每个事件一个概率，再做推断。本次离线实验每个事件本来就只有一行。

## 统计

离线参照是规则映射减先导期常数基率的平均配对 Brier。另外两条零差值对照是规则对农历月基线、规则对同月的**单次**固定置换。Holm 只调整这两条“差是否为 0”的蒙特卡洛比例。它不调整百分位区间，也不检验差是否超过 0.02。农历月基线减常数基率只描述，不进这个家族。

区间是按 ISO 周重抽样的事件加权近秩百分位，10000 次，只作探索性描述。单年序列仍有季节性，相邻周仍可能相关，区间可能偏窄。极端次数写成 `extreme_count/mc_n`，并给出该比例自己的 Wilson 区间。0/10000 不是精确的 p，也不是 p<0.0001。同月对照只有一条 HMAC 置换，区间没有包含置换分布的随机性。主体只有结算网格这一个。

0.02 只是阅读幅度的参照。区间含 0 不是等效。bootstrap 区间自己的覆盖率无法用这一次样本估计。

## 复现

```bash
python3 -m pip install -r research/requirements.txt
sh research/reproduce.sh
```

等价的分步命令：

```bash
python3 -m pytest research/tests -q
python3 -m research.cli verify-offline
```

还没有快照时，`verify-offline` 的位置换成 `run-offline`。`run-offline` 只在结果目录为空时下载一次 Open-Meteo 并写文件；之后拒绝覆盖。重新下载会变成另一次结算，本命令不做这件事。

单次起卦：

```bash
python3 -m research.cli cast-numbers --year-branch 5 --month 12 --day 17 --hour-branch 9
python3 -m research.cli cast --utc 2024-02-09T16:00:00+00:00
python3 -m research.cli serve --port 8765
```

服务只监听 127.0.0.1，只起卦，不结算，不调用模型。
